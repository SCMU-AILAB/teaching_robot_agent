## R1 / P1：清理中的 CancelledError 会杀死唯一执行器

位置：`runtime/action_manager.py:350`，`_execute()` 清理阶段只捕获 Exception。

触发：设备 stop 或 Skill.cleanup 自身抛出 asyncio.CancelledError，例如底层 SDK 异步操作被取消。CancelledError 属于 BaseException，不会进入现有失败处理。

复现：注入 stop 抛出 CancelledError 的模拟适配器，提交有效移动。得到 `status=verifying`、`blocked_reason=None`、执行器任务已结束；等待动作终态超时。

影响：动作没有终态，任务取消与等待者可能永久挂起；执行器已死亡，但 Runtime 仍可能接受新动作入队。无法确认停止时也没有进入阻止后续动作的状态。

建议：清理取消单独处理，保证记录失败、设置阻塞、通知所有等待者；执行器退出需有明确监督和拒绝提交机制。回归应覆盖清理自己取消以及队列中还有第二个动作。

## R2 / P1：立即停止可能使控制台永久保持忙碌

位置：`agent/robot_host.py:56`、`:103`，`app/robot_console.py:35`、`:68`，以及 TeamGateway.next_input。

触发：输入已经入队，process_next 尚未进入 handle 注册 `_workers` 时调用 cancel。队列消费者跳过已取消输入后继续等待；cancel 只能取消 `_workers` 中的内部处理协程，无法结束外层队列等待者。

复现顺序：create_task → submit_text → host.cancel → app.process_next。最后一步持续等待，被复现脚本 50ms 的外部期限截断。

影响：控制台 show_reply 对应 worker 仍未结束，后续普通输入被判断为“当前任务处理中”；再发 /stop 也找不到内部 worker，必须退出控制台。现有停止测试先等待模型开始，错过了这个窗口。

建议：按任务关联从排队到执行的整个请求生命周期；控制台 stop 同时结束本请求的外层等待者，或让队列对被取消请求返回明确取消结果。不要依靠跳过条目来结束一次性请求。

## R3 / P1：模型没有实际完成动作也能使任务 completed

位置：`agent/robot_host.py:160`，`agent/embodied_agent.py` 中无工具调用时返回 AgentTurn 的分支。

触发：用户要求“先观察，再前进”，模型只输出“我将调用观察工具，然后向前移动”，没有真正返回 tool_calls。宿主立即调用 finish_interaction。

复现：`task_status=completed`，动作数量为 0，最近观察为 None。

影响：界面和上层系统看到任务完成，但用户要求的观察、移动没有发生；模型提出澄清问题时同样会关闭任务，无法在原任务继续回答。文档把 completed 限定为“请求处理结束”并不能解决执行目标未完成的问题。

建议：把模型最终回答、等待用户、继续执行、目标完成分成显式结果；含动作或观察目标的完成判定应依赖可核对的事实。纯问答可以零动作完成，但不能仅按“本轮没有工具调用”判断所有任务完成。

## R4 / P1：执行与停止验证不检查遥测时间

位置：`skills/base.py:23`、`:45`，`skills/move_relative.py:85`，`runtime/action_manager.py` 的 `_cleanup()`。

触发：适配器缓存数据不更新，仍返回 connected=True、moving=False 和一个位姿；执行层完全不检查 RobotState.updated_at。

复现：适配器将所有状态时间固定为 Unix 时间 1.0，一次正常动作仍被标记 succeeded，完成证据 observed_at 为 1.0。

影响：接入真实 SDK 后，旧的静止状态可能被当成当前停止确认，旧位置也没有被标记不可信。当前距离与角度校验并不能证明遥测是本次命令之后采集的。

建议：在适配器契约和执行层落实状态新鲜度、单调序列或命令后反馈要求；过期或无效时间不得确认完成/停止。阈值按硬件能力配置，避免沿用模拟器精度。

## R5 / P2：显式 observation 绕过最新场景失效标记

位置：`agent/context.py:62`，`agent/embodied_agent.py:95`。

触发：调用者持有观察对象后提交运动，再将原对象传给 ContextBuilder。Gateway 使用 replace 给缓存对象标记 stale，但原对象仍是 stale=False；Builder 优先采用显式参数，仅比较两秒时间。

复现：同一观察 `gateway.latest_observation(...).stale=True`，显式传入后 `context.observation.stale=False`。

另一个同源问题：宿主把观察传入 decide 后，该观察被整个工具循环固定使用；模型再调用 observe_scene 得到新结果，也不会替换此处显式上下文。模型可能同时看到旧上下文和新工具结果。

建议：统一按场景版本和当前运动状态检查任何观察，显式参数不能绕过；轮次内观察工具完成后应更新权威上下文，而非永远优先使用最初参数。

## R6 / P2：动作续接丢失本轮意图与查询到的知识

位置：`agent/robot_host.py:196`，`agent/embodied_agent.py:92`。

触发：模型先查安全知识再提交动作。动作完成后调用 decide(observation=...)，没有用户输入；_decide 又创建空 history，前半轮知识工具结果丢失。

复现：任务目标为“家庭陪伴任务”，本次输入为“先查插座知识，左转，再根据刚才查到的知识讲解”。捕获续接模型的输入后确认原始输入不在其中、知识内容不在其中、user_input=None。

影响：通用 API 的目标和用户本轮输入不一定相同，模型可能忘掉后续步骤；即使控制台将目标设为输入文本，动作前查到的来源也不保留，移动讲解不能稳定引用已获取的知识。

建议：保存按任务的当前请求和已完成步骤/工具事实；以“动作完成事件”续接同一意图，防止重复执行应通过动作账本或幂等控制，而不是删除原始上下文。

## R7 / P2：模拟感知产出的 PNG 文件损坏

位置：`perception/simulated.py:17`。

复现：读取模拟帧证据，调用 Pillow Image.verify，返回 `broken PNG file (bad header checksum in b'IDAT')`。

影响：图片有 PNG 文件头，但不符合项目自身 VLM 适配器的图像校验；模拟相机/证据与真实视觉提供者组合联调会失败。现有测试只检查 PNG 文件头，无法发现文件损坏。

建议：替换为实际可解码的占位图，并增加完整 verify/load 测试以及证据到视觉适配器的组合测试。

## R8 / P2：默认主应用积压未消费的动作事件

位置：`runtime/action_manager.py:85`、`:228`，`app/robot_application.py:30`。

所有动作状态都 put 到无界 `_events` 队列，但默认 RobotApplication 不装配 ActionEventHub，也没有 next_event 消费者；wait_for_action 只等待 `_done`，不会消费这些事件。

复现：完成 10 个各含一个动作的任务后，事件队列保留 40 个事件。宿主同时保留 10 个终结任务的 Agent；输入结果和任务记录也没有保留期。

影响：长时间运行不断累积事件和状态，无界事件队列尤其不是业务记录保留所必需的数据。

建议：主应用实际装配并关闭事件桥，或者采用订阅者感知的事件发布/有界历史策略；终结任务对象、去重记录和动作记录设定保留上限。EvidenceStore 的 64 MiB 拒绝写入是已声明限制，但没有释放接口，真实图片接入时也需要明确证据保留策略。
