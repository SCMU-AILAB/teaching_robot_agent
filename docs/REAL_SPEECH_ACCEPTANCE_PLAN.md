## T1 真人声音验收（最优先）

### 1a 语料（20 句，负责人已确认）

覆盖知识库 7 类加控制指令；不含"陌生人敲门"（知识库无对应条目）。

| 类别 | 句子 |
| --- | --- |
| 热水壶 | 热水壶能碰吗？／热水壶里的水烧开了吗？ |
| 插座 | 那插座呢？／可以把充电器插在那个插座上吗？ |
| 刀具 | 剪刀可以自己拿吗？／用完的刀具应该放在哪里？ |
| 药品 | 抽屉里的药丸能吃吗？／找不到药盒怎么办？ |
| 燃气灶 | 燃气灶能自己开吗？／燃气灶用完要检查什么？ |
| 清洁剂 | 清洁剂能喝吗？／八四消毒液和洁厕灵能混着用吗？ |
| 窗户阳台 | 可以爬上窗台看外面吗？／阳台的护栏能翻过去吗？ |
| 学习陪伴 | 这道题怎么列方程？／帮我听写第五课的单词。 |
| 控制指令 | 停下／别动了／大点声／重复一遍刚才的答案 |

### 1b 离线评测脚本（已完成，待实测）

已实现 `tools/eval_asr.py`：录音先存为 WAV 文件（不入仓库），评测脚本按 `--engines` 对同一批 WAV 逐引擎识别，自动计算字错率与耗时，输出 Markdown 结果。真实 SenseVoice 引擎端到端冒烟通过；Whisper 对比评测需提供 faster-whisper 模型目录。7 项纯逻辑测试覆盖 CER、语料读取与汇总。

### 1c 实测执行

2–3 人 × 20 句 × 4 条件（近距离/远距离 × 安静/背景噪音）。录音人匿名编号，录音文件不入仓库。

### 1d 统计口径

字错率为编辑距离除以参考字数；识别耗时从结束指令到文本返回（模型常驻，无加载延迟）。产出实测数据表，如实标注已测与未测条件。

## T2 TTS 方案确定（与 T1 并行）

比赛运行机器已确认：机器人主控为 ESP32-S3-WROOM-1-N8R8（PCB 已迭代至 v0.5 PCBA，I2S 麦克风与功放）。ESP32-S3 无法运行 SenseVoice、Whisper 或任何中文 TTS 推理，因此识别与合成必须在服务器或随行 Mac 上执行，ESP32 只负责 I2S 采音与播放。

候选对比：sherpa-onnx VITS（与识别引擎同框架、进程内常驻、零新增依赖框架）、Piper（适配器已有，服务器已部署）、系统合成（仅限随行 Mac 场景）。核心对比指标改为**首包延迟与流式播放**（合成侧到 ESP32 出声），其次音质、服务器资源占用、许可证（各中文 TTS 模型训练数据与许可证不同，对比表须写明）。

产出选型对比表，经负责人拍板后才实现；实现时遵守"模型加载不进模块导入、依赖进可选 extra"约定。

## T3 SSH 远端链路去留（决策项）

依据 T1 实测数据决策，决策权在负责人。比赛机器确认为 ESP32-S3 后天平变化：若比赛现场不随行 Mac，识别与合成只能走服务器，SSH 链路可能从"冻结"转为"必选"；两处遗留问题（每次请求重建 SSH、无协议版本校验）在多轮现场交互下影响放大，保留决策需一并评估补齐成本。

## T4 交互改进（先方案、经审核后实现）

与记忆系统开发存在同文件冲突：双方都会修改 `app/robot_console.py`。节奏约束——4a 方案先交记忆系统开发方查看，其合入后开工前先同步 main；4b 涉及 RobotHost 播报流程，方案同步抄送。

- 4a VAD 自动断句（替代 `/record`、`/done`）：首选 sherpa-onnx silero-vad（与现有依赖同框架、进程内）；方案写清检测参数、误触发与漏触发边界、与录音生命周期的衔接。
- 4b 开口打断播放：改变录音与播放互斥规则，必须先在 `docs/MODULE_CONTRACT.md` 写出条款草案（标注待审核），经负责人确认后才实现。设计要点：打断时播放侧停止确认、租约抢占语义、被打断回答终态（cancelled 而非 failed）、与 SpeakSkill 停止失败的交互。

## T5 HTTP/SSE 合同起草（最后）

## 交付纪律（每个 PR 通用）

1. 四项检查全部通过：`uv run ruff check .`、`uv run ruff format --check .`、`uv run basedpyright`（零错误零警告）、`uv run python -m unittest discover -s tests -v`。
2. 不得通过 ignore/noqa、排除业务或测试文件绕过问题。
3. 分支使用 `feature/xxx`、`fix/xxx`；提交采用 `<type>(<scope>): <subject>`；以后语音相关工作一律从最新 main 开新分支。
4. main 变更只经负责人审核后的合并请求完成；PR 说明明确区分已真机验证与未验证内容。
5. 涉及接口：先改合同、经确认、再实现。
